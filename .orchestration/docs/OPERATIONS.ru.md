# Эксплуатация

[English](OPERATIONS.md) | Русский

## 1. Команды

| Команда | Назначение |
|---|---|
| `orch.py quota [--refresh]` | квоты всех агентов с источником и достоверностью |
| `orch.py route <role> [--heavy\|--light]` | пробный выбор агента с причиной |
| `orch.py prefer <role> <agent\|->` | ручное переопределение следующего выбора (снимается `-`) |
| `orch.py dispatch <task.md> --role <r> --id <id>` | запуск воркера; `execute` получает worktree |
| `orch.py wait [--timeout S]` | ожидание события воркеров |
| `orch.py collect <id> [--keep-worker]` | проверка доказательств, коммит worktree, остановка воркера |
| `orch.py worktree merge\|remove\|path <id>` | слияние или отказ от ветки `orch/<id>` |
| `orch.py status [--json]` | снимок состояния |
| `orch.py hub start\|stop\|restart` | публикатор для Herdr App в отдельном терминале |
| `orch.py watch` | тот же публикатор с выводом дашборда в текущий терминал |
| `orch.py tools`, `orch.py tool-ask <module> "<запрос>"` | tool-агенты хаба |
| `orch.py advice [--json]` | подсказки владельцу: сжатие или очистка контекста, смена владельца, обновление шаблона |
| `orch.py owner set <agent> [--launch] [--space caller\|project] [--force]` | передача роли владельца (раздел 5) |

## 2. Локальные переопределения

`.orchestration/agents.local.toml` и `.orchestration/routing.local.toml` не коммитятся и сливаются поверх
основных файлов. Пример: модель и уровень рассуждения Codex, статический бюджет агента без зонда квоты.

```toml
[agents.codex]
command = ["codex", "--no-daemon", "-m", "<model>", "-c", "model_reasoning_effort=high"]

[agents.codex-review]                # вариант модели на той же учётной записи
command = ["codex", "--no-daemon", "-m", "<review-model>"]
capabilities = ["review"]
cost_tier = "premium"
quota = "codex"                      # общий замер квоты с [agents.codex]
quota_windows = ["5h"]               # недельное окно видно, но не ограничивает
stability = "supported"

[agents.kimi]
stability = "supported"          # после smoke-теста
quota = "static"
quota_static = {remaining_percent = 100}
```

## 3. Воркер ждёт человека

`dispatch` сообщает `startup.ok: false`, если агент не сообщил статус за 25 с. Типичные причины:
диалог доверия к корню проекта (первый запуск агента в проекте), вход в учётную запись.
Ответ даёт человек в Herdr App или через `hc attach w-<id>`. Владелец не нажимает клавиши за человека.

Ручная проверка запущенного воркера: `hc get w-<id>` показывает `state = live`, значение `status.state` (агент
сообщает его через OSC 7501 после загрузки интерфейса) и метку `herdr.space` (вкладка есть в App). У прямого
`hc run` в выводе JSON есть также `first_message.sent`; `dispatch` передаёт первое сообщение аргументом, поэтому
оно не теряется, пока агент загружается.

Статус `blocked` во время работы означает запрос разрешения. Он виден в App, дашборде и в ответе `orch.py wait`.

## 3.1. Воркер Codex падает с `bwrap: execvp .../codex`

Codex выполняет команды оболочки, запуская собственный бинарник внутри песочницы bwrap. Если активный профиль
прав (`default_permissions` в `~/.codex/config.toml`) запрещает `":root"` и не даёт песочнице читать установку
Codex (для автономного установщика - `~/.codex/packages`), любая команда падает до запуска, и воркер
останавливается без отчёта. `codex exec` с явным `-s` скрывает проблему: старый режим песочницы заменяет
профиль и открывает чтение всей файловой системы.

Исправлять профиль, а не команду воркера: убрать запрет `":root"` и запретить только пути секретов
(`"~/.config/secrets" = "deny"`) либо разрешить чтение установки Codex. Проверка - `codex sandbox -- /bin/true`;
`./scripts/doctor.sh` выполняет её, если в реестре есть агент Codex.

## 3.2. Вкладки воркеров в Herdr App

При `[workers] show_in_app = true` каждый воркер и запущенный владелец получают вкладку; скрытых нет.
`[workers] space` выбирает пространство:

| Значение | Пространство |
|---|---|
| `caller` (по умолчанию) | пространство терминала, выполнившего `dispatch` (владельца); если этот терминал не показан в App (запущен через `hc run`, вне Herdr App), пространство проекта |
| `project` | пространство, вкладки которого сейчас работают внутри репозитория (текущая папка его терминалов, как в Mission Control); если такого нет, создаётся с одной вкладкой |

App хранит раскладку в документе ядра `herdr-app`; терминал с меткой `herdr.space=<id>` получает там
вкладку. Сохранённое поле `folder` пространства - папка, в которой оно создано, и за `cd` оно не
следует, поэтому используется только как запасной вариант. Текущая папка терминала - `foreground.cwd` из `hc get`
(папка программы, работающей в нём); поле `cwd` - папка, в которой терминал запущен. Имя вкладки берётся из
`--name` (`w-<id>`); метка `where`, если задана, даёт подпись вкладки. Закрытие вкладки воркера завершает
воркера; задача остаётся, `collect` сообщает о ней.

## 3.3. Передача владельца: доступ команд и runtime

`HC_TERMINAL_ID` подтверждает унаследованный адрес терминала, но не доступ к core. Codex может
быть виден в Herdr, а его shell tool получать `EPERM` при подключении к Unix-сокету core.
`--no-daemon` удерживает исполнение в терминале, но не выдаёт права на сокет, кеш или Git.
Проверять `hc get "$HC_TERMINAL_ID"` нужно инструментом команд новой агентской сессии, а не только
в запускающей оболочке. Ошибка systemd после отказа подключения не доказывает остановку core.
Перезапуск core и ручное исполнение вместо GSD-воркеров не являются исправлением этого отказа.

У целевого агента явно задаётся `gsd_runtime` в `agents.toml` или локальном override, в том числе
для произвольного id владельца. `owner set` согласованно меняет `routing.toml` и GSD `runtime` в
`config.json`, сохраняя прочие настройки. При `--launch` сначала проверяется доступ вызывающего
к core; отказ `hc run` восстанавливает оба файла. `--force` отменяет только проверку свежести handoff.
Запущенный терминал ещё не означает проверенную среду. Новый владелец выполняет пробу core,
`orch.py hub start` и `orch.py status --no-planning` до dispatch. Затем проверяются вкладка, space,
родитель и Mission Control, а также безопасный запуск воркера, отчёт и collect.
Вызов без `--launch` меняет настройки и не проверяет новую сессию.

Профиль прав должен разрешать фактический сокет core, кеш оркестратора, метаданные Git и команды
проекта. Пути и выбор прав хранятся в игнорируемой локальной конфигурации. Расширение прав
согласуется с пользователем; публичный шаблон не включает неограниченный доступ по умолчанию.
Codex поддерживает именованные профили и правила Unix-сокетов; применимость зависит от платформы
и версии: https://developers.openai.com/codex/config-reference . После изменения профиля может
потребоваться новая сессия; доступ проверяется повторно её инструментом команд. Переменные среды
и успешный запрос escalation сами по себе не доказывают доступ к сокету.

Квотный допуск проверяется отдельно: `orch.py route execute` может отказать после ремонта доступа,
если прогноз расхода воркера с резервом нового владельца общей учётной записи слишком велик.
Резервы при ремонте среды не снижаются. Отказавший dispatch должен оставаться читаемым в status;
задача без запущенного воркера имеет состояние failed, а не running или complete.

## 4. Восстановление после перезапуска

- Сессия владельца: `orch.py status` показывает незавершённые задачи; `collect` по каждой.
- Перезагрузка машины или ядра: herdr-core не возобновляет агентов. Задача без живого терминала и без
  отчёта получает `incomplete` в `collect`; worktree и ветка остаются для ручного разбора.
- `hub` перезапускается командой `orch.py hub start` (это делает старт сессии владельца). Hub завершается сам, если папка проекта удалена или в проекте нет живого терминала (панель App, владелец, воркер) в течение `[watch] idle_exit_minutes` (по умолчанию 60, 0 отключает).

## 5. Передача роли владельца

Поводы: владелец исчерпывает квоту своего вендора (`orch.py advice` предлагает смену при остатке ниже `advice.owner_switch_percent`, по умолчанию 10%, и называет агента проекта с возможностью `owner` и наибольшим остатком) или решение человека.

1. Безопасная граница: задачи собраны или их можно оставить идущими (новый владелец соберёт их), решения по ревью записаны.
2. Текущий владелец выполняет `/gsd-pause-work`: GSD записывает `.planning/HANDOFF.json` и `.continue-here.md` и коммитит их.
3. GSD для нового владельца установлен официальным установщиком (`npx @opengsd/gsd-core@<pin> --<runtime> --local`); для Codex пересмотрен защитный блок `.codex/config.toml`.
4. `orch.py owner set <agent> --launch` проверяет возможность `owner` и свежесть `HANDOFF.json` (не старше `advice.handoff_max_age_minutes`), меняет `owner` в `routing.toml` и GSD `runtime` в `config.json`, затем запускает нового владельца вкладкой в пространстве вызывающего терминала (`--space project`: пространство проекта, см. ниже). `--force` пропускает проверку, если прежний владелец недоступен.
5. Новый владелец выполняет `/gsd-resume-work` и `orch.py status`; оба изменения настроек коммитятся вместе с передачей.

## 5.1. Гигиена контекста владельца

Каждый запрос владельца повторно отправляет весь контекст, поэтому стоимость запроса растёт с размером контекста. `orch.py advice` и блок Advice в Mission Control сообщают размер контекста владельца (Claude: statusline через `statusline-tap`; Codex: журнал сессии) и предлагают `compact_command` агента после `advice.compact_tokens` (по умолчанию 100 тыс.) и `/gsd-pause-work` с `clear_command` после `advice.clear_tokens` (160 тыс.). Подходящая точка: нет идущих воркеров или задачи только что собраны; посреди фазы допустимо на такой точке. Команды сжатия и очистки задаются в `agents.toml` для каждой среды.

Если последнее низкое значение квоты владельца устарело, но его окно ещё не сбросилось, Advice показывает условный совет о передаче роли. Перед `/gsd-pause-work` нужно подтвердить текущую квоту; автоматическая маршрутизация по устаревшему значению не выполняется. Щелчок по команде в Advice копирует её в буфер обмена (App в Windows). Кнопка перезапуска в заголовке Mission Control запускает `orch.py hub restart` и обновляет публикатор состояния.

## 5.2. Обновление шаблона

`.orchestration/template.toml` хранит версию шаблона проекта и адрес репозитория. Hub раз в `advice.update_check_hours` (24 ч), при запуске и при смене фазы сравнивает её с последним тегом `vX.Y.Z` (`git ls-remote --tags`) и при новой версии показывает подсказку. `orch.py advice` тоже проверяет тег заново. Обновление выполняет человек через `scripts/install-into-repo.sh` нового выпуска.

Возможность быть владельцем подтверждается тестом в целевой среде, а не предполагается.

## 6. Внешние ресурсы worktree

Скопировать `.orchestration/hooks/worktree-env.example` в `.orchestration/hooks/worktree-env`, сделать исполняемым
и настроить изоляцию БД, портов и кэшей. Хук вызывается после создания каждого worktree.

## 7. Обновление зависимостей

Версии не меняются только потому, что вышел новый выпуск.

1. Изменить `.orchestration/versions.env`.
2. Прочитать примечания к выпуску каждого обновляемого компонента.
3. `./scripts/version-check.py --strict`.
4. Переустановить GSD официальным установщиком.
5. `./scripts/reconcile-runtime-config.py`.
6. `./scripts/self-check.sh --offline`.
7. Smoke-тест воркера через herdr-core: `orch.py dispatch` задачи `research`, затем `execute` в worktree, `collect`, `worktree merge`.
8. Обновить `.orchestration/docs/COMPATIBILITY.md` и `REVIEW.md`.
