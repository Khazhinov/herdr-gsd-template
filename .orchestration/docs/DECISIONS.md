# Архитектурные решения v0.2

| # | Решение | Обоснование | Альтернатива и причина отказа |
|---|---|---|---|
| D1 | Python 3.11 stdlib, конфигурация в TOML | `tomllib` в stdlib, существующие скрипты на Python, ноль зависимостей | YAML требует PyYAML; JSON без комментариев |
| D2 | Один CLI `scripts/orch.py` и пакет `orchlib` | одна точка входа для агента-владельца; тестируемые модули | набор shell-скриптов v0.1 плохо тестировался |
| D3 | Квота Codex из `codex app-server` (`account/rateLimits/read`) | живые данные за 1 с без активной сессии Codex; журналы остаются запасным путём | только журналы сессий: устаревают между сессиями |
| D4 | Квота Claude из входа statusline (`rate_limits`) через tap | официальный источник, обновляется при каждом ответе владельца; пользовательская строка сохраняется цепочкой | недокументированный OAuth-эндпоинт usage отклонён |
| D5 | Устаревшая квота (> 30 мин) считается неизвестной для маршрутизации; владельцу показывается условный совет при последнем низком остатке до сброса окна | тяжёлая работа не опирается на старые данные; низкий остаток до сброса окна может только уменьшиться | использовать последнее значение для автоматического выбора: может завысить остаток |
| D6 | Одноразовый воркер на задачу (`hc run`), без `/clear` и перезапусков | свежий контекст по умолчанию, cwd задаётся при запуске | постоянные peer-панели v0.1 |
| D7 | Воркер не коммитит, коммит в `collect` | песочница Codex защищает `.git` | `danger-full-access` противоречит безопасным значениям по умолчанию |
| D8 | Завершение через `hc wait --children` и отчёт, без обязательного `hc send` | `hc send` из песочницы требует подтверждения | обязательное оповещение блокировало бы воркера |
| D9 | Worktree внутри репозитория | наследование доверия папки, без диалога у безлюдного воркера | `~/.herdr/worktrees` (соглашение App) требует доверия на каждый worktree |
| D10 | Дашборд как мод Herdr App, реактивный через метки терминала hub | без опроса, данные ядра живые, мод не хранит бизнес-состояние | опрос `exec` по таймеру: лишние перерисовки и задержка |
| D11 | Встроенные `plan_check` и `code_review` GSD выключены в профиле lean | ревью выполняет независимый воркер с учётом квот | встроенные линии `/gsd-review` вызывают CLI разово, без квот: оставлены для профиля strict |
| D12 | Мост `cross_ai_command` реализован, но выключен | GSD исполняет делегированный план в корне без worktree; владелец теряет контроль ревью до слияния | включение по умолчанию |
| D13 | Kimi, OpenCode и ZCode в реестре как `candidate`/`experimental` | Kimi и ZCode не прошли smoke-тест; OpenCode прошёл smoke-тест роли `research`, исполнение в worktree не проверено | объявить поддержку без проверки |
| D14 | Резерв проверяется по прогнозу остатка после задачи: остаток минус ожидаемый расход идущих задач той же учётной записи минус расход новой задачи. Расход измеряется при `collect` (`quota_burn`), оценка - медиана последних 5 задач, шедших в одиночку; иначе `reserves.*.<вес>_cost_percent` (по умолчанию 0); оценка ограничена `99 - резерв` | полевой случай 2026-11-02: две параллельные тяжёлые задачи допущены при одних и тех же 77%, третья при 36% исчерпала окно 5 ч | сравнение текущего остатка с резервом пропускает задачу, которая сама съест резерв |
| D15 | Контракт задачи содержит правила расхода квоты: длинная команда - один вызов с максимальным ожиданием, без опроса `ps`/`tail` | каждый вызов инструмента повторно отправляет весь контекст сессии; в полевом случае опрос дал 102 из 138 запросов и 82% входных токенов | ограничение на стороне CLI: недоступно |
| D16 | Допуск задач всех проектов сериализован через `admission.lock`; `ledger.json` хранит активные задачи и образцы расхода по учётной записи, весу и окну | два проекта не должны одновременно занять один лимит; отсутствующие терминалы и записи старше 24 ч удаляются при чтении | локальные списки задач не видят другой проект |
| D17 | Кэш квот хранит исходное чтение по учётной записи; фильтр окон и статический бюджет применяются в проекте; после сброса без нового наблюдения окно неизвестно | проектные настройки не меняют общее чтение и старые проценты не притворяются новой квотой | кэшировать готовое решение для каждого агента |
| D18 | Прогноз и медиана последних пяти одиночных задач считаются отдельно для каждого окна; начальные оценки 15% и 3%; на учётной записи владельца добавляется резерв 10% | короткое и длинное окна расходуются с разной скоростью, владельцу нужна ёмкость для управления | единый минимальный остаток и нулевая оценка |
| D19 | `collect` останавливает воркера до коммита; с `--keep-worker` не коммитит; `.planning/` запрещена в ветке и worktree; merge проверяется до удаления worktree | исключает запись после проверки и потерю изменений при конфликте | удалять worktree перед пробным merge |
| D20 | Повторный id требует `--replace` с архивированием записи и отчёта; `dispatch --of` исключает учётную запись автора при независимом ревью | доказательства старой задачи сохраняются, ревью не попадает автору через другой вариант агента | повторно использовать id и сравнивать только имена агентов |
| D21 | Передача роли владельца опирается на `/gsd-pause-work` и `/gsd-resume-work` GSD; `orch.py owner set` проверяет свежесть `.planning/HANDOFF.json` и меняет только `owner` | формат передачи уже есть в GSD и понятен любой среде с установленным GSD | собственный файл передачи: дублирование GSD |
| D22 | Подсказки владельцу (`orch.py advice`) только советуют; сжатие, очистка и смена владельца выполняются человеком | действия меняют сессию человека и необратимы для её контекста | автоматическая очистка: теряется контекст в неподходящей точке |
| D23 | Размер контекста владельца: Claude из statusline (`context_window`, запасной путь - журнал сессии), Codex из журнала сессии; для других сред подсказка о контексте не выводится | официальные источники без опроса модели | оценка по числу сообщений: неточна |
| D24 | Проверка обновлений шаблона: тег `vX.Y.Z` через `git ls-remote --tags`, кэш 24 ч, без автоматического обновления | работает без `gh` и токена; проект знает свою версию из `.orchestration/template.toml` | GitHub API: лимиты и токен |
